# Integration architecture

> **Status: Designed. Not Implemented.** Phase 9.

Integrations must never be coupled to domain logic. Findings do not know Jira exists. The
domain emits events; the integration layer subscribes and translates.

```
domain service ──▶ DomainEvent ──▶ outbox ──▶ integration dispatcher ──▶ provider adapter
```

The outbox pattern matters here: events are written to an `OutboxEvent` table **in the same
transaction as the change**, then relayed by a worker. Without it, a committed change with a
failed dispatch silently diverges from every downstream system.

## 1. Provider interface

```ts
interface IntegrationProvider {
  id: string
  displayName: string
  authType: 'oauth2' | 'api_key' | 'webhook'
  supportedEvents: DomainEventType[]
  configSchema: ZodSchema            // renders its own settings UI
  connect(ctx, params): Promise<Connection>
  disconnect(ctx, connectionId): Promise<void>
  test(ctx, connectionId): Promise<TestResult>
  handle(ctx, event, config): Promise<DeliveryResult>
}
```

Adding a provider means implementing this and registering it. It touches no domain code — if
it does, the abstraction has leaked.

## 3. Credentials

OAuth tokens and API keys are encrypted at rest with the application key
([`../security/secrets.md`](../security/secrets.md)), never returned by any API, never
logged, and scoped as narrowly as the provider allows. OAuth refresh happens in a worker with
a lock so concurrent jobs cannot race a refresh. Disconnecting revokes the token upstream
where supported, not merely locally.

## 4. Bidirectional sync

Two-way sync creates loops. Guards: every write records its origin, and an inbound change
matching a change we just made is ignored; a version or hash comparison detects genuine
divergence; conflicts resolve **in favour of Sentinel for security fields** (severity, status
lifecycle) and in favour of the external system for its own fields (assignee, sprint).
Mappings are explicit and configured per connection — never inferred.

## 5. Outbound webhooks

Customer-defined endpoints, the most security-sensitive integration because the customer
chooses the destination.

- Signed: `X-Sentinel-Signature: t=<ts>,v1=<hmac-sha256(secret, ts + "." + body)>`, with the
  timestamp inside the signed material so replay is detectable.
- Secret generated by us, **shown once**, rotatable with an overlap window.
- **SSRF rules apply to delivery targets**: HTTPS only, public addresses only, DNS resolved
  and checked before connecting, redirects not followed.
- Retries with exponential backoff up to 24 h; delivery log retained with request, response
  status, and timing; an endpoint failing persistently is auto-disabled and the customer
  notified.
- Creating an endpoint requires `webhook.create` — an elevated permission, because an
  endpoint is a data exfiltration channel by design.

## 6. Failure isolation

An integration failure never fails the domain operation that triggered it. Dispatch is
asynchronous, retried, logged, and surfaced in the integration health view. A broken Jira
connection must not prevent a finding being created — the finding is the product; the Jira
issue is a convenience.
