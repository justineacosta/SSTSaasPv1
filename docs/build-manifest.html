Part I — Frame

01What this document is

A manifest, not an architecture. The architecture blueprint answered how — the tenancy model, the trust boundaries, the queue semantics, the engine contract. Those decisions are settled and recorded as ten ADRs in the repository. This document answers the next question, which is the one you actually schedule against: what are the discrete things that have to be built, and in what order?

Every table below is an inventory. Where a count appears, it is a count of things that must exist for the product to work — not an estimate, and not padding. Where something does not exist yet, it says so.

How to read the phase markers

done is built and verified by running it, not merely written. P2 is the phase currently queued. P4 and above are committed but not started. A status moves only after the phase’s exit criteria have been executed and their real exit codes read; the evidence for the two that have moved is in §3.

The four things that make this build different from ordinary SaaS

Ownership verification gates everything. An asset cannot be scanned until the customer has proven they control it. This is the single unskippable step in onboarding, and it is why §8 has an AssetOwnershipVerification table and §12 has a verification endpoint group before any scanning endpoint exists.

Scope is evaluated twice. Once at the API for feedback, once inside the worker immediately before traffic leaves. That means the scope evaluator is a shared library used by two callers, not a controller method — a structural consequence that shows up in §4.

Findings are identities. A finding persists across scans; each detection attaches as an occurrence. This has to be right from the first scan ever run, because the history is not reconstructible afterwards. It is why §25 is a pipeline with six named stages rather than an insert.

Engines hold nothing. No credentials, no tenant identity, no database access. They read a job on stdin and write JSON on stdout. That is what makes §23's twelve engine categories a plugin list rather than twelve architectures.

Why packages/scope is its own workspace

The scope evaluator is called from the API (for user feedback) and from the worker (as the authoritative check before traffic leaves). Those two callers must produce byte-identical decisions, forever. Putting the evaluator in a shared package with its own table-driven test suite makes divergence a compile error rather than a subtle behavioural drift that nobody notices until a scan reaches something it should not have.

Non-negotiable

The security job runs on every pull request, not nightly. It is the gate that makes tenant isolation a property of the system rather than an intention, and the registry check is what stops its coverage rotting as the schema grows. No merge on red — not with an override, not for "unrelated" failures, not for flakiness. A flaky test is quarantined and fixed.

The five tables that carry the most design weight

Asset — the unit of "a thing we may test"

Nine types, criticality, environment, owner, tags. The field that matters most is ownershipVerifiedAt: null means no scan may target it, enforced at the API and again in the worker. Unique on (organizationId, projectId, type, normalizedValue) so the same asset cannot be registered twice with cosmetic differences.

ScopeVersion — why scope is immutable once referenced

Editing a scope creates a new version rather than mutating rules in place. A scan records the scopeVersionId that authorised it, so months later we can answer "what permitted this?" exactly. This matters for audit, and it matters more for disputes.

Finding + FindingOccurrence — the dedup model

The single most consequential schema decision in the product. Finding is the vulnerability; FindingOccurrence is one sighting. Unique on (organizationId, assetId, fingerprint). Triage state lives on the finding and survives every rescan — a decision made in January is not erased by a scan in August.

AuditEvent — append-only at the database level

The application role holds INSERT and SELECT and no UPDATE or DELETE grant, revoked by migration, with a trigger as a second barrier. Tampering requires DBA credentials, not an application bug. Events are written in the same transaction as the change they describe.

Entitlement — the flat projection

One row per (organizationId, key) with a source of PLAN, OVERRIDE, or PROMOTION. The application asks what an organisation is entitled to; it never asks what plan they are on. This is what makes grandfathering and enterprise deals a data change rather than a code change.

Partial indexes are used aggressively for status-filtered queries, because open findings are a small fraction of total findings in a mature tenant and that fraction is what the product looks at constantly.

Constraints that live in the database

  • Foreign keys on every relation with deliberate ON DELETE: CASCADE for owned children, RESTRICT where deletion should be refused, SET NULL for optional references.
  • UNIQUE on (organizationId, slug), (organizationId, userId) for membership, the finding fingerprint, API key hash, session token hash.
  • CHECK on severity/CVSS agreement, finishedAt >= startedAt, non-negative counters, and ownershipVerifiedAt IS NULL OR ownershipVerificationMethod IS NOT NULL.
  • Optimistic concurrency version integer on Finding and Scope so two triagers cannot silently overwrite each other.
  • RLS enabled on every tenant table, policy on current_setting('app.organization_id'), application role not BYPASSRLS.

Three separations that look odd until you need them

AUDITOR reads the audit log but not evidence. A compliance reviewer must prove that testing happened and findings were verified. They rarely need the vulnerability detail, and evidence routinely contains the customer's own secrets and PII. Least privilege says separate them; an auditor who genuinely needs evidence gets VIEWER alongside, as a deliberate act.

MEMBER cannot accept risk. Accepting a risk is a business decision with compliance weight, not a triage action.

MEMBER cannot run aggressive scans. Potentially disruptive testing is a separate decision from routine scanning.

Invariants enforced in code: a custom role can hold only permissions its creator holds; an API key only a subset of its creator's, and never organization.delete, organization.manage_roles, billing.manage, or apikey.create; a role change takes effect on the next request, not at a cache TTL.

Authorization is applied per event at send time, not once at handshake, so a demoted user stops receiving events they may no longer see. The client uses events to invalidate query keys and refetch through normal authorised endpoints — the realtime channel can never become a second, less-guarded way to read data.

Never simulate

The UI never advances a progress bar on a timer. If the stream drops, the interface says so and falls back to polling. In a security product, the difference between "this scan is running" and "this scan was running when we last heard" is a real difference, and pretending otherwise is the interface lying about system state.

The design thesis these are built against

The interface is quiet so the findings can be loud. In a triage queue the most important signal is severity, and severity is communicated by colour. If the chrome around it is also saturated, severity stops meaning anything and the user loses the one visual channel doing real work.

So the colour budget is spent in exactly one place. Chrome, navigation, surfaces, and typography are near-neutral cool ink tones. Saturated colour is reserved for severity, status, and destructive intent, and appears nowhere else — not in empty-state illustrations, not in chart defaults, not in a hero gradient. This rules out the dark-terminal-with-neon-accent look most security products adopt, which is fun and is also why everything in the category feels alarming at 4pm on a Thursday when nothing is wrong.

Severity is never conveyed by colour alone. Every indicator carries the glyph and the text label — a WCAG requirement, and also how the product stays readable in a printed report, a screenshot pasted into Slack, and a greyscale PDF.

Payloads carry identifiers, never authority

{ "scanId": "scn_01J...", "organizationId": "org_01J...", "requestId": "req_01J..." }

organizationId is present only so the worker can assert it matches what it loads. A mismatch means a bug or a forgery attempt and fails loudly. Everything else — scope, entitlements, verification, cancellation — is re-read from Postgres at execution time, because all of it can change between enqueue and execution and the stale copy would be the one that ran.

The worker re-validation sequence

1.  Load scan by id.                          missing → fail, alert
2.  Assert payload org == loaded org.         mismatch → fail, alert loudly
3.  Assert organisation active, not suspended.
4.  Assert subscription and entitlements permit execution.
5.  Assert status is QUEUED and not cancelled.
6.  Load asset; assert exists, not deleted, ownership verified.
7.  Load the referenced scope version; re-evaluate every target.
8.  Validate engine config against the pinned version's schema.
9.  Only then: mark RUNNING and execute.

Authorization, scope, and entitlement failures are never retried. The refusal was the correct answer; retrying a refusal is exactly backwards.

25Finding pipeline

Six stages between an engine emitting a candidate and a row appearing in the findings table. All six are platform concerns, never engine concerns — that is what makes findings from different engines comparable. 

raw finding
  → 1 normalise   taxonomy lookup, canonical text, location canonicalisation
  → 2 verify      HIGH accept · MEDIUM re-probe once · LOW retain but suppress
  → 3 fingerprint deterministic SHA-256 over normalised inputs
  → 4 deduplicate upsert Finding, always append Occurrence
  → 5 evidence   upload artifacts, link metadata, redact at capture
  → 6 risk       severity x criticality x environment x exposure x confidence
  → transaction: persist + audit → realtime event → notification

Fingerprint normalisation — where the work is

Input Normalisation
Host Lowercase, trailing dot stripped, IDN to punycode, default port removed
Path Percent-decoded then re-encoded canonically, duplicate slashes collapsed
Query Parameter names only, sorted. Values excluded — ?id=1 and ?id=2 are one vulnerability
Path IDs Numeric and UUID segments → {id}. The highest-leverage rule — without it an IDOR check over a hundred user IDs produces a hundred findings of one defect
Code location File path + symbol, never line number — lines move, the vulnerability does not
Dependency Package + ecosystem + vulnerability ID, not installed version

Never in a fingerprint: timestamps, scan IDs, session tokens, nonces, CSRF values, response bodies, payload values, line numbers, severity. A fingerprint containing a volatile value produces a new finding every scan, which is the bug this entire design exists to prevent.

Three ingestion behaviours worth stating plainly

  • Reopening always notifies. A vulnerability returning after being fixed is the most important event the system can report.
  • FALSE_POSITIVE and ACCEPTED_RISK are never overridden by a scan. A machine does not overrule a human's triage decision. The occurrence is still recorded, so the history stays honest, but the status and the silence hold.
  • An existing OPEN finding generates no notification. Re-notifying about known issues is how alerting gets muted.
Auto-resolution has a qualification that matters

A finding not seen by a scan is only a resolution candidate if that scan's check completed successfully. A scan that failed, timed out, or ran a different profile proves nothing about the finding's absence. Each scan records which checks completed; a finding needs two consecutive qualifying misses before it resolves, with an activity entry and a notification — never silently. Manual findings are never auto-resolved.

Microservices The domain is aggressively relational. Splitting it buys distribution problems and sells transactional integrity. ADR-0001.
GraphQL Consumers are a first-party frontend and enterprise CI integrations that want stable, versioned, documented endpoints.

Client-side authorization as a control It exists only as a UX affordance. Hiding a button is not a security control.

Shipping web and API security well, with deduplication that works and evidence people trust, is the version of this that succeeds. Twelve engines that each half-work is the version that gets churned out of.

That is a scope recommendation, not a refusal. Say the word and any of them moves forward.

Three decisions rev 1.0 did not know about

ADR-0011 — Prefixed UUIDv7 identifiers, generated in application code

IDs are time-ordered for index locality and carry a type prefix (fnd_, scn_) so a misrouted identifier is obvious in a log rather than an opaque hex string. Generated in application code, not the database, so an ID exists before the insert and can be referenced inside the same transaction.

ADR-0012 — Node 26 pinned for development and CI, engines >= 22

The host runs Node 26, ahead of what should ship. Pinning development and CI to one version while declaring a wider engines floor keeps local, CI and production honest with each other without forcing every consumer onto the bleeding edge.

ADR-0013 — A 24-hour release-age cooldown on every dependency

The most interesting of the three, because it was discovered rather than designed. pnpm 11 defaults to a 1440-minute minimum release age; that default reddened CI four times before anyone wrote it down, presenting as an unexplained 30-second install failure. It is now declared explicitly in pnpm-workspace.yaml with its rationale and its cost.

The failure taught something sharper than the control itself: a warm tree cannot observe this failure class. With node_modules in sync, pnpm prints “Already up to date” in 277ms and never runs the check, so three local install variants passed while CI died from cold. It is the clearest argument in the repository for verifying exit criteria the way they are written — from a clean clone — which is why §3’s evidence table does exactly that.

One implementation note that contradicts a shipped decision

ADR-0006 changed during implementation

The original decision said the tenant-scoped Prisma client would rewrite findUnique into a scoped findFirst, closing the most common multi-tenant bug. It shipped, then changed. Rewriting invokes a different client method, which cannot be guaranteed to run on the same connection or transaction as the original call — inside withTenantTransaction that silently broke read-your-own-writes and put the rewritten query on a connection with no RLS setting.

The shipped implementation runs findUnique unmodified, which stays on the correct connection by construction, and checks the tenant column on the result. Same guarantee, different mechanism. The ADR carries the note rather than being quietly edited, because the reasoning is more useful than the tidy version.

A second gap surfaced the same way: Organization is the tenant root, has no organizationId of its own, and was missing from the original decision. It needs both isolation layers too, scoped by id.

What has not changed

Every architectural decision from rev 1.0 still holds. The engine contract, the double scope evaluation, the finding-identity model, the entitlement projection, and the three-layer tenancy design are all intact — ADR-0006’s note is a change of mechanism, not of guarantee. The counts in §§8–27 remain the design targets; what moved is how much of them exists.
