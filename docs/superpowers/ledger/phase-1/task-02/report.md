## Deviations from the brief (both required, not stylistic)

1. **Removed the unused `import { z } from 'zod'` in `env.spec.ts`.** The brief's test file
   never references `z` in the test body. With `eslint.config.js`'s
   `recommendedTypeChecked` ruleset, this is a hard lint error
   (`@typescript-eslint/no-unused-vars`). No test assertion, export name, or behaviour
   changed — one dead import line removed.

2. **Fixed a real bug in Task 1's `eslint.config.js`, discovered while running `pnpm
   lint`.** Every package's `tsconfig.json` (per the brief, including this task's own)
   excludes `src/**/*.spec.ts` from the build project, so that `tsc -p tsconfig.json`
   never emits test files into `dist`. But `eslint.config.js` used
   `parserOptions: { projectService: true }` with no accommodation for that exclusion —
   typescript-eslint's project service auto-discovers projects from each directory's
   `tsconfig.json`, and a file excluded from every discoverable project fails outright:
   `Parsing error: ... was not found by the project service`. This is not
   `packages/config`-specific; it will hit **every** future package's spec files the same
   way (Tasks 3+).

   Fix: added `projectService.allowDefaultProject: ['packages/*/src/*.spec.ts',
   'apps/*/src/*.spec.ts']`, which gives matched files an isolated single-file
   type-checked program instead of the excluded package project.

   Also added `'@typescript-eslint/no-unused-vars': ['error', { ignoreRestSiblings: true
   }]` — the brief's own "names every missing variable" test uses
   `const { DATABASE_URL, REDIS_URL, ...incomplete } = validApi;` to build a negative
   fixture, an idiomatic pattern the default rule (no `ignoreRestSiblings`) flags as
   unused variables.

   **Known limitation I could not fully resolve**: typescript-eslint hard-rejects `**` in
   `allowDefaultProject` globs (`Parsing error: ... contains a disallowed '**'`, citing
   performance). I tried `packages/*/src/**/*.spec.ts` first (matching
   `vitest.workspace.ts`'s own include glob) and it failed with that exact error, so I
   fell back to single-star globs (`packages/*/src/*.spec.ts`), which only reach spec
   files directly under a package's `src/`. A spec file nested one directory deeper (e.g.
   `apps/api/src/modules/auth/auth.spec.ts`) will hit the same "not found by the project
   service" error and need its own explicit glob entry added to `eslint.config.js` at that
   point. I left a comment in `eslint.config.js` flagging this for whoever hits it next.

Both changes are additive/scoped: `ignoreRestSiblings` only affects the specific
destructure-to-omit idiom (a true unused variable is still caught), and
`allowDefaultProject` only affects files matching those two globs (nothing else in the
existing type-aware lint coverage was loosened). Verified with a probe: `pnpm exec eslint
.` is clean (0 problems) across the whole repo after both fixes, and I did not disable
`recommendedTypeChecked` or drop type-aware linting for spec files anywhere.

## Fix report: coordinator override — replace allowDefaultProject with a per-package tsconfig split

### What changed and why

The coordinator overruled the `allowDefaultProject` fix from the original report. That
fix worked for `env.spec.ts` but does not scale: typescript-eslint hard-rejects `**` in
`allowDefaultProject` globs, so only spec files directly under a package's `src/` were
covered. Five later tasks (9, 10, 11, 12, 13) put specs in subdirectories
(`apps/api/src/common/filters/...`, `packages/ui/src/components/...`, etc.) and would
each have hit the same "not found by the project service" error, requiring a fresh glob
entry in `eslint.config.js` every time. There was also a real defect underneath it:
`packages/config/tsconfig.json` excluded `src/**/*.spec.ts`, and `pnpm typecheck` runs
`tsc -p tsconfig.json --noEmit` against that same file, so no spec file was ever
typechecked. A type error in a test would never fail the build.

**Fix: split each package's tsconfig into a typecheck/lint config and a build config.**

- `packages/config/tsconfig.json` now has `include: ["src/**/*.ts"]` with no spec
  exclude. This is what ESLint's `projectService` discovers and what
  `tsc -p tsconfig.json --noEmit` typechecks. `rootDir`/`outDir` unchanged.
- `packages/config/tsconfig.build.json` (new) extends `./tsconfig.json` and excludes
  `src/**/*.spec.ts`, `src/**/*.spec.tsx`, `src/**/*.integration.spec.ts`. This is the
  only config that emits.
- `package.json` scripts: `build` now runs `tsc -p tsconfig.build.json` (was
  `tsconfig.json`); `typecheck` still runs `tsc -p tsconfig.json --noEmit` (unchanged
  target, but now actually covers specs since the exclude moved out of `tsconfig.json`).
- Same split applied to the shared preset: `tsconfig/library.json` dropped its spec
  exclude; new `tsconfig/library.build.json` extends it and adds the exclude, so a
  future package extending `@sentinel/config/tsconfig/library.json` for its own
  `tsconfig.json` and `@sentinel/config/tsconfig/library.build.json` for its own
  `tsconfig.build.json` gets the same property for free, restating its own
  `rootDir`/`outDir`/`include` as `packages/config/tsconfig.json` already does (see
  the path-resolution check below for why that restatement is necessary).
- `eslint.config.js`: removed `allowDefaultProject` entirely, reverted to
  `parserOptions: { projectService: true, tsconfigRootDir: import.meta.dirname }`, and
  replaced the comment with one explaining the split rather than the workaround.
  `ignoreRestSiblings` on `@typescript-eslint/no-unused-vars` was kept as-is; the
  coordinator confirmed it and the dropped unused `z` import were both correct.

## Fix report: reviewer finding — loadEnv leaked enum values, and the guard test was vacuous

### The finding

Reviewer reproduced, against the real schema on zod@3.25.76: `sharedEnvSchema.safeParse`
on an invalid `APP_ENV` produces an issue whose `.message` is Zod's own default text,
e.g. `"Invalid enum value. Expected 'development' | 'test' | 'staging' | 'production',
received 'super-secret-value'"` — the raw invalid value verbatim. `load-env.ts` built its
thrown error's detail by joining `issue.message` per issue, so every `z.enum(...)` field
(`NODE_ENV`, `APP_ENV`, `LOG_LEVEL`, and `STORAGE_FORCE_PATH_STYLE`, built on
`z.enum(['true','false'])`) leaked its actual invalid value into
`EnvValidationError.message`, contradicting the class's own doc comment.

Compounding it: `env.spec.ts`'s "never includes a variable value in the error message"
test set `DATABASE_URL: 'postgresql://user:hunter2@bad'` — that value satisfies
`.min(1).startsWith('postgresql://')`, so `loadEnv` never throws, the `catch` block never
runs, and the `expect` inside it never executes. The test was green regardless of whether
the leak existed.

### Fix — safe by construction, not by audit

Rewrote `packages/config/src/load-env.ts` to stop reading `issue.message` entirely.
Added `describeIssue(issue: ZodIssue): string`, a `switch` over `issue.code` that builds
each detail line from fields whose shape is fixed and schema-authored — `expected`,
`options`, `minimum`/`maximum`, `validation` rule parameters, issue codes — and never
from a field that can carry the parsed input:

- `invalid_type`: uses `expected`/`received`, but for this issue code both are
  type-category tags (`"string"`, `"undefined"`, `"nan"`), never the value itself.
  Confirmed by inspecting zod's own `ZodError.d.ts`, where `ZodInvalidTypeIssue.received:
  ZodParsedType` — a closed set of type-tag strings.
- `invalid_enum_value` / `invalid_union_discriminator`: uses `options` (the allowed
  values — schema-authored, safe, and useful for fixing the `.env`) and deliberately
  never reads `.received`, which the type definition (`ZodInvalidEnumValueIssue.received:
  string | number`) confirms holds the raw input.
  `invalid_literal`: uses `.expected` only, never `.received` (same shape: `received:
  unknown`).
- `invalid_string`: uses `.validation` (a closed enum of rule names like `"url"`, or an
  object like `{ startsWith: "postgresql://" }` — the *rule's own parameter*, authored
  in `env.ts`, not user input).
- `too_small`/`too_big`/`not_multiple_of`: numeric rule parameters only.
- Every other code (`unrecognized_keys`, `invalid_union`, `invalid_intersection_types`,
  `invalid_arguments`, `invalid_return_type`, `custom`, and an unreachable `default`)
  returns a generic, code-only description with no interpolation of anything
  input-derived.

The doc comment above `describeIssue` states explicitly that this is deliberate:
auditing which Zod issue codes happen to produce safe message text is a check that
silently expires on the next Zod version bump; owning the strings does not need Zod's
cooperation to stay safe.

Verified every schema-reachable issue shape directly against the installed
`zod@3.25.76` before writing the switch (temporary script run from inside
`packages/config/`, deleted after): reproduced `invalid_type` (missing field, bad port),
`too_small` (empty string), `invalid_string` (bad `startsWith`, bad `url`),
`invalid_enum_value` (bad `APP_ENV`, bad `STORAGE_FORCE_PATH_STYLE`), `too_big`
(port out of range), and confirmed the exact JSON shape of each issue object, not just
its message text — e.g. `{"code":"invalid_enum_value","received":"...","options":[...],
"path":["APP_ENV"]}`, confirming `.received` is the field to avoid and `.options` is safe.

### Test changes

In `packages/config/src/env.spec.ts`:

1. **Fixed the vacuous `DATABASE_URL` test.** Changed the input from
   `'postgresql://user:hunter2@bad'` (passes validation, never throws) to
   `'mysql://user:hunter2@bad'` (fails `.startsWith('postgresql://')`, genuinely
   throws). Added an explicit `expect(() => ...).toThrow(EnvValidationError)` before the
   `try`/`catch` so the test fails loudly if it ever stops throwing again, rather than
   silently passing with an empty catch body.

2. **Added a targeted enum test** — `'rejects a secret-looking APP_ENV value, naming the
   variable and the allowed options but never the value'`. Feeds `APP_ENV` the sentinel
   `S3CR3T-SENTINEL-VALUE`, asserts it throws `EnvValidationError`, asserts the message
   names `APP_ENV` and lists the allowed options (`development`, `staging`), and asserts
   the sentinel itself is absent.

3. **Added the property test** — `'never leaks a sentinel value into the error, for any
   field in the schema'`. Iterates `Object.keys(apiEnvSchema.shape)`; for each key,
   builds a candidate env with that one field replaced by the sentinel, calls `loadEnv`,
   and — whether it throws or not — records the key in a `leaked` array if the sentinel
   appears in `error.message` or any entry of `error.variables`. Two final assertions:
   `expect(throwCount).toBeGreaterThan(0)` (so the test cannot degenerate into a
   no-op loop where nothing ever throws and the leak check never runs) and
   `expect(leaked).toEqual([])` (so a failure names every leaking key at once, not just
   the first).

Test count: 6 → 8 (one test's body changed in place, two added).
