What “Implemented” does not mean

The foundation is finished. The product does not exist.

Implemented here is a claim about Phase 1’s exit criteria and nothing wider. Nothing is deployed, and no request reaches this code from outside a test or a developer’s own machine.

  • No authentication. The only API routes are health probes and the OpenAPI document.
  • No authorization enforcement. @RequirePermission() is metadata no guard reads yet — it records an intention.
  • Rate limiting governs nothing. It is correct and tested, in advance of the endpoints it will police.
  • No product UI. Two pages, deliberately with no mock metrics or seeded findings.
  • The CI artefact-upload path has never executed — it only runs on failure, and nothing has failed.

Two defects the verification pass found

Both were the same defect wearing different clothes: a gate whose correctness depended on ambient machine state. Neither was visible from a warm tree, which is exactly why they survived so long.

Defect Why it hid Fix

The E2E suite tested whatever server held the web port reuseExistingServer attached to a stale next dev server — different environment, report-only CSP, possibly older code. Its own port on a separate env schema, and reuse switched off entirely once measurement showed it saved nothing.

Still open

  1. Branch protection dies if the repository returns to private. main is now gated on the verify check with administrators included, but on this plan a private repository cannot carry protection at all. Flipping visibility back removes the gate silently — nothing announces it.
  2. The release-age trap is documented, not removed. Any dependency added within 24 hours of publication will red CI until it ages out. That is the control working; the response is to wait or pin the previous release, never to add an exclusion.
  3. id.ts’s own docstring example is not a valid ID. Wrong length, and it contains characters the Crockford alphabet excludes, so the parser rejects it. A one-line fix, deliberately left so it can be done deliberately.

A note on how this was verified

Phase 1 ran subagent-driven: a fresh implementer per task, then a separate adversarial reviewer. Across Task 16 and the hardening that followed, those reviews found zero Critical defects — and repeatedly found something else.

Every commands-and-output check reproduced exactly under independent re-run. What did not hold up was the prose written about them: false factual claims in newly authored text, including one that reintroduced a wrong number inside the very paragraph rewritten to correct it, and one where a design rationale was asserted with a plausible figure that measurement showed did not exist. The pattern is consistent enough to be worth stating plainly: the commands were never the problem. Citation discipline — naming the command or file behind each assertion — is the only control that catches this class, because no test does.

Sentinel — authorised security testing against customer-owned assets only. Scope enforcement and proof of ownership are the platform’s core safety control, not features.
